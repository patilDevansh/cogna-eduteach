# MVP 2.0 — Production Auth

> MVP 1.0 used dev auth. MVP 2.0 needs production auth paths for pilot, while keeping local development simple.

## Roles

| Role | Auth path |
|---|---|
| Parent | Clerk account |
| Student | Access code under parent account |
| Admin/reviewer | Clerk account with admin metadata |

Students do not need email/password accounts in MVP 2.0 unless pilot requirements change.

## Clerk Requirements

Environment:

```text
CLERK_SECRET_KEY=
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=
CLERK_WEBHOOK_SECRET=
```

API behavior:

- verify parent JWT for parent routes
- allow dev fallback only when `NODE_ENV !== "production"`
- map Clerk user ID to `User.clerkId`
- reject missing/invalid JWT in staging/prod

## Student Access Code

Access code remains:

- generated by parent
- hashed in DB
- case-insensitive on login
- revocable by parent/admin

## Guardian Invites

MVP 2.0 supports invite stub or simple invite:

```text
POST /parents/me/students/:studentId/invite
```

Minimum behavior:

- create pending parent-student link
- record invited email
- send invite email if provider configured

## Billing Link

Billing status may be stubbed or Stripe-backed:

```text
trial
active
past_due
cancelled
```

Billing must not block local dev.

## Security Requirements

- parent can only view linked students
- report endpoints enforce parent-student link
- admin/reviewer routes require admin metadata
- no raw access code stored
- consent record required before practice

## Tests

- parent cannot view unlinked student
- invalid JWT rejected in production mode
- dev fallback disabled in production mode
- student access code is case-insensitive
- revoked access code cannot login
